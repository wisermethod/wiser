# Gateway

How this plugin reaches an outside account: hosted inside the Wiser endpoint, or as the one local process a harness attaches, as `standards/primitives.md` Connector Bodies states. `standards/primitives.md` defines the connector type it serves; `gateway/SETUP.md` says how a person reaches each; `gateway/providers/AGENTS.md` says how a provider plugs in. This file is the local gateway's write inventory and the gateway's contract with the rest of the root.

## What the gateway is

Not a primitive. Skills and experts invoke connectors by action id, `service.module.action`, and the gateway is how those ids are served: it loads every connector's manifest and module, resolves each id in a fixed order, applies the policy, and either runs the action or answers with a status object that names the next step. It holds no credential. The provider holds the grant; the local-file provider reads a bound credential file and hands the module nothing.

**This is the authoritative list for the gateway and the connectors it loads.** `tools/AGENTS.md` carries the inventory for tools and points here; neither restates the other.

`--home` is canonicalised before any of that is written, and refused inside this plugin, inside the directory that holds `--env` or a `--secret` file, under `--secrets`, or on a symbolic link; the store and audit files refuse to write through a symbolic link as well.

Nothing is written inside this plugin. The gateway has no dependencies, so it installs nothing, and a connector module may not install anything either.

**Three things the gateway never writes**, stated because their absence is the design: a secret value, anywhere; the input or output of an action, except an action's declared file output written only in `outputs/` as listed above; a file inside the plugin. An empty `KEY=` template at the default path is not a secret value.

## What a connector module receives, and may do

A module is `connectors/<service>/index.js`, exporting `modules`, a map of module name to a map of action name to `async (input, ctx) => result`. The manifest beside it declares every action the gateway will serve; the validator refuses a module that exports more or fewer.

`ctx` carries `service`, `module`, `action`, `input`, and four capabilities:

| Capability | What it does | When it exists |
|------------|--------------|----------------|
| `ctx.catalog(actionId, input)` | Runs the provider's own tool for this id, mapped by the provider adapter. The module never sees the slug | When the module's `auth.provider` is `catalog` |
| `ctx.proxy({ endpoint, method, body, parameters, binary_body })` | An authenticated HTTP call the provider makes on the module's behalf. The provider enforces its own same-domain rule | Same |
| `ctx.http(request)` | A direct HTTPS call with the credential attached by the gateway. The module never sees the value. HTTPS only, to a host the manifest's `auth.hosts` lists, and a redirect is refused rather than followed | Only when the manifest says `unwrap_token: true`, lists `auth.hosts`, and the provider can unwrap; in v1 that is the local-file provider |
| `ctx.audit(note)` | Reserved. The audit line is a closed field set so a module cannot put a secret on it; in v1 the call is accepted and the note is dropped | Always |

A module imports Node built-ins and files inside its own directory, and nothing else. It never imports a provider, never reads a credential file, never names a provider slug, and never writes a file. What it needs beyond `ctx`, it does not need.

An action declaring `response_headers` receives those names on `ctx.proxy`'s answer as `headers`, under the `proxy` row of `gateway/providers/AGENTS.md`.

`ctx.proxy` delivers a response body as JSON or as text, never as bytes. A binary body, such as raw audio, comes back with HTTP 200 as a string with the undecodable bytes replaced, and nothing in the answer marks it broken: measured 2026-10-20 on xAI's text-to-speech, whose raw MP3 arrived as 1.95 million characters, 712,907 of them U+FFFD. A module that needs bytes asks the vendor for a JSON or base64 form of them and decodes and checks what arrives; a 200 is not evidence the bytes survived.

A file-output action declares `output_file: { media_types, max_bytes }` in its manifest. The slot never reaches an answer by another way: a status object the module returns, or a status it throws, has any `output_file` member removed first. `media_types` is a non-empty list of distinct keys from the closed extension table in `src/file-output.js`; `max_bytes` is a positive safe integer. The module returns `output_file: { media_type, data }`, with `data` a `Buffer` or `Uint8Array`, beside its other result fields, and still never writes a file. A status object carries no slot. The gateway replaces a valid slot with `file: { path, bytes, sha256, media_type }`. Without an explicit absolute `outputsDir`, it answers `local_only` after a policy denial has been checked and before reading the connection store or calling a provider. Only the stdio serve supplies that option; `--route` and `--call` do not, and `--check` constructs no gateway.

## The resolution order

Code, in `src/resolve.js`: a connector module that declares the action; else a registered first-party classifier loaded by `--classifier`; else the catalog through the mapping; else `needs_connector`. A `wiser.*` id with no classifier loaded answers `needs_subscription` rather than `needs_connector`. The order is not configurable, because a person reading a status needs to know which step answered.

## First-party classifier

Optional. Loaded by `--classifier <abs dir>`, the same shape as `--connectors`: an absolute path to a directory outside this plugin, repeatable, screened as absolute. The directory is not a connector and carries no `manifest.json`. It exports `createClassifier({ envPath, packsDir, thresholdsPath })`, which returns `{ name, actions(), describe(id), roster(rows), execute({ actionId, arguments, key }) }`. `name` is the directory's name. `key` is the classifier credential from the platform key file, handed at call time; the first-party path does not write it to `process.env`.

**What it serves.** The five action ids `wiser.route.roster`, `wiser.route.ask`, `wiser.gate.check`, `wiser.decide.choice`, `wiser.recall.rank`. `wiser.recall.rank` and `wiser.gate.check` have no caller in this plugin today. `search_actions` and `describe_action` list them when a classifier is loaded, and do not mention them when none is. A host that reads tools meets them there; a host that reads instructions meets `wiser.route.ask` in the constitution. When a classifier is loaded and `search_actions` is given a query, it may put one `wiser.decide.choice` through the first-party execute path and list an accepted action first. A choice is accepted only when it is one of the listed ids and its confidence is at least `SEARCH_PICK_BAND` (0.51), the lowest confidence at which the pick was as precise as a host choosing on a calibration set of its own; below it, today's results stand and the result says `below-band`. It takes no `owning_root`. The session binding that supplies the root is `hooks/AGENTS.md`.

**Every first-party execution is gated on that binding** before any input is handed to the adapter. The paths are MCP `execute`, the call `search_actions` makes, and one-shot `--call` and `--route`, and the roster call is gated the same way. The long-running server identifies the harness by its parent process, because its own session id is the one from startup. A one-shot process takes `CLAUDE_PID` and `CLAUDE_CODE_SESSION_ID` as `hooks/AGENTS.md` states, including the ancestor check. It sends only when the binding verifies, is not refused, names exactly one owning root, and that root is not refused at send time. Otherwise the answer is `classifier_unbound` with a `reason`, the adapter is not called, and the audit line is written as for any other first-party refusal. No environment variable turns the gate off. `search_actions`, when that gate fails, returns today's results and `classifier: { path: 'builtin', reason }`; no query, or no classifier loaded, stays today's search and sends nothing.

**The published `search_actions` description** is the text from before this seam when no classifier is loaded. When one is loaded, the list answered by `tools/list` may add one sentence of at most 120 characters that an accepted pick is listed first and marked. The descriptor is chosen when that list is answered.

**Roster handshake.** The client sends primitive rows once to `wiser.route.roster` and receives a digest; it sends the digest with `wiser.route.ask`. On `roster_unknown` it re-sends the rows once and retries once. A row is `{ family, name, description, body }`; `body` is the primitive's full text.

**Privilege, risk, confirmation.** Every first-party action is `read` / `low` / `none`: they read nothing durable and change nothing. An executable first-party action requires an explicit gateway declaration in `FIRST_PARTY_ACTIONS`; an id the adapter advertises that the gateway does not declare is `needs_connector` with `reason: undeclared`, not invented as `read`. `policy.default.json` names a rule `{ role: "*", service: "wiser", privilege: "read", op: "execute", effect: "allow" }` above the trailing wildcard. That named rule matches first and authorises the call. The trailing wildcard is what would admit it if the named rule were removed. A person's `policy.json` can still deny or confirm a classifier call; the confirmation stop is preserved and composes its summary from this metadata, not from a manifest row.

**Statuses it can answer.** Gateway statuses: `needs_subscription` (no classifier loaded, or the `WISER_CLASSIFIER_KEY` line of the platform key file is empty), `classifier_unbound` (a first-party call was not sent for want of a verified session binding; the `reason` is the verifier's, `not-ancestor`, `refused`, or `no-owning-root`; `hooks/AGENTS.md` is the list), `needs_confirmation` (a policy rule demanded it), `denied`, `invalid_arguments`, `needs_connector` (an advertised `wiser.*` id the gateway does not declare). Adapter-level answers that are not gateway statuses and live inside the result: `unavailable`, `below_threshold`, `roster_unknown`. An adapter that throws is converted to `unavailable` with a fixed reason, never the exception message, and is not propagated. A thrown `StatusSignal` is that same conversion; the first-party path does not return the thrown object. `needs_subscription` is a gateway status; the others in that adapter-level list are not. An unrecognised adapter status is audited as `classifier_other` rather than copied into the log.

**The key.** `WISER_CLASSIFIER_KEY` on the platform key file `SETUP.md` names. The gateway reads it from that file and nowhere else, and hands the value to the adapter at call time as `key` on the execute request. An empty line is no key. The first-party path does not mutate `process.env`.

**The two version facts.** Every first-party execute writes `model` and `calibrated_model_version` on the audit line, including a roster call, an uncalibrated refusal, and a call that returns before the adapter (`needs_subscription`, `invalid_arguments`, `needs_confirmation`, `needs_connector` / `undeclared`, `denied`). The values are taken from `result.meta` before any conversion of the result, so a `vendor_error` mapping cannot drop a model the adapter supplied. A member is kept only when it is a non-empty string of at most 128 characters, and is null otherwise: absent `meta`, a non-string, an empty string, and a longer string are null. Omitting either key is the failure. `meta` is `{ model, bar, calibrated_model_version }`, present on every adapter result, and it is not part of any action's answer. `model` is the last envelope the call read: a non-empty string, the string `unknown` when an envelope was read and its `model` is not one, or null when no envelope was read. The string `unknown` is kept as that non-empty string; the gateway does not invent it from a non-string. `bar` is the dotted path of the bar a probability was compared against (`routing.door_r2`, `routing.target_r2`, `gate.T_fail`), or null when no comparison happened. A value that is not one of those three paths is null. `calibrated_model_version` is that bar's version, including null where the bar carries null, and null when `bar` is null. The two selections come apart: an alias compares a bar without posting, and a malformed envelope can be read without a comparison. A version mismatch stays the adapter's status object. The line records `unavailable` for it and does not record `reason`, `calibrated_on` or `answered_by`. On a mismatch, `calibrated_model_version` is the checked bar's version.

**The answer.** Each first-party action declares its success shape beside its input in `FIRST_PARTY_ACTIONS`, and the gateway checks the adapter's result against it. A result that fails answers `{ status: 'unavailable', reason: 'malformed answer' }`. The reason is fixed. Nothing is rounded, defaulted or coerced, and the adapter's message is not copied. The check does not apply to a gateway status, to `unavailable`, `below_threshold` or `roster_unknown`, to any other adapter status string, to a `vendor_error` result, or to the reserved `meta` key. A `below_threshold` that names `p` must name a probability; a missing `p` is left as the adapter returned it. `wiser.route.ask` allows `confidence: null`.

## The published input schema, and who applies it

**The gateway applies it, once, for every connector, and no connector carries a validator of its own.** `execute` reads the action's `input` from the manifest and refuses a call that does not satisfy it with `invalid_arguments` and the name of the first field at fault. The code is `src/input-schema.js`, which states what it reads, `type`, `enum`, `pattern`, `minLength`, `items` and `required`, and what it leaves to the module, `maxLength`, `minimum`, `maximum`, `oneOf`, `anyOf` and anything nested. **A key `properties` does not declare is refused**, which is why every shipped action declares `additionalProperties: false`: the published schema and the applied rule say the same thing.

**Until 2026-09-20 nothing applied it.** `src/manifest.js` type-checks that `input` is an object and validated no call against it, so the module was the only enforcer and the schema was documentation. Eleven connectors carried a byte-identical copy of this code; the other fourteen hand-rolled their checks and held all 189 divergences `test/agreement.test.js` measured. A connector cannot import the gateway, because `--connectors <abs dir>` lets a connector directory sit anywhere on disk, so the choice was twenty-five copies or none.

**Where it sits in `execute` is a decision, and each side of it was measured.** After the policy, so a denied action's input is never inspected. After the grant checks, so a caller with no connection is told that rather than told about its arguments, which is the common case and the one the whole connect flow serves. Before the confirmation stop, so nobody is asked to approve a call that cannot run.

**Two gates in `test/` measure connectors rather than the gateway, and both belong here.** They
read every shipped connector, so they live where the loader does rather than in a family that
ships no test runner: `agreement.test.js` holds a manifest against its module, and
`guide-conformance.test.js` holds every connector guide against `connectors/shared-text.md` and
against the rule that no shipped guide carries operator state. Neither touches an account; both
are ratchets whose baselines may only shrink.

**`test/agreement.test.js` holds the two sides together.** It calls every shipped action behind this validator with a schema-valid instance and with one violation per declared constraint, and fails on a divergence in either direction. Its baseline may only shrink, so the file going empty is the class closing.

## What the confirmation stop shows, and what it does not

A `needs_confirmation` answer is the one place a person decides. **It carries the values of the declared fields the call was given**, arrays and objects included, so an approval names the thing being acted on rather than only the shape of the call. Before 2026-09-20 it carried field names and no values. Before 2026-09-27 an array or object was named and not rendered, and `confirm: true` was accepted for any input.

The rule has four parts and they are separate on purpose.

**Eligibility** decides which values may appear. The key is declared in the action's `input.properties`, and some member of its declared `type` matches the value's JSON type: `array` for an array, `object` for a non-null non-array object, `null` for null, and `string`, `number`, `integer` or `boolean` for those scalars. A mismatch is withheld with reason `type`. An **undeclared key is counted and nothing more**: neither its name nor its value appears anywhere in the answer.

**Depth.** A value nested deeper than 32 levels is withheld with reason `depth` and is never rendered. The limit is what keeps a hostile input off the stack. The top-level value is level 1.

**Plain JSON.** An array or object must be plain JSON all the way down: finite numbers, strings, booleans, null, arrays with no holes, and plain objects with no `undefined` member. Anything else, a `NaN`, an `Infinity`, an `undefined`, a hole, a `Date`, a bigint or a function, is withheld with reason `not_json`, because it would render one way, key the approval another and reach the connector as a third. A call arriving over MCP cannot carry one; a caller using the gateway directly can.

**Validation** checks an eligible scalar against its own declaration before rendering it. A scalar that fails is withheld and named. An array or object is rendered whatever its schema says. Validation is **not** what makes the summary safe.

**Rendering** is what makes it safe. A string is double-quoted and escaped. A number is `String(n)`. A boolean is `true` or `false`. Null is `null`. An array is `[e1, e2, e3]`, elements joined by `", "`. An object is `{"key": value, "key2": value2}`, keys in the order the input gives them, each key quoted and escaped like a string, `": "` between key and value, `", "` between members. Nesting uses the same forms. Every value is escaped against the Unicode classes `Cc`, `Cf`, `Cs`, `Zl`, `Zp` and `Default_Ignorable_Code_Point`, plus the backslash and the double quote. Each value's text is capped at 120 characters. A cut is marked with the true length and a sha256 fingerprint of 16 hex characters, and the cut is on a whole escape token, never inside one or inside a surrogate pair. For a scalar the length and the fingerprint are of the raw value. For an array or object they are of the complete rendered text. The summary's every component is budgeted so the 2000-character limit holds unconditionally.

**The full text.** When a value is truncated, its `input_values` entry carries `full`, the complete rendered text, escaped and quoted as `value` would be without the cap. When it is not truncated, the entry has no `full` key. The summary names each shortened field and says the full text is in `input_values`. That clause is budgeted with the other warnings, so it survives the 2000-character cap. No raw unsafe code point appears anywhere in the status object. A stored account id that contains one never reaches that object: `disconnect` refuses it before any stop, and the id is not copied onto the refusal. A safe id is still returned raw, because the caller echoes it back.

**What it does not show:**

- **A scalar that fails its own declaration.** Named as withheld, with the keyword it failed.
- **Anything from an undeclared key.**
- **A value past the depth limit.** Named as withheld, with reason `depth`.
- **A structured value that is not plain JSON.** Named as withheld, with reason `not_json`.

Since 2026-09-20 the published input schema is applied before this stop, so a scalar failing its own `pattern`, `enum`, `type` or `minLength`, and an undeclared key, are both refused with `invalid_arguments` and never reach a person. `undeclared_fields` is structurally 0. The renderer goes on handling both, because `discloseInput` decides what a person is told and has to be safe on its own terms rather than on the strength of a caller having passed an earlier gate.

When a call needs approval, on the connector path and on the first-party path, disclosure is computed before any stop and before the confirmation key. If it withheld any field, for any reason, including `depth`, `not_json`, a failed `maxLength`, `minimum`, `maximum`, `multipleOf`, or any other, the call returns `invalid_arguments` with `field` set to the first withheld field's name and `reason` set to that withheld reason. No pending approval is recorded, and nothing runs, with or without `confirm`. A stop never offers an approval for a value it did not show. A call that needs no approval does not consult that check and is unchanged.

**What the refusal itself carries.** `invalid_arguments` names the field at fault, and for an undeclared key that field name is one the caller chose. `AUDIT_FIELDS` has no `field`, so neither the name nor the value reaches `audit.jsonl`.

**Three residuals, stated so they are not mistaken for oversights.** A caller may put a secret into a declared free-form string and no rule here can tell; provider credentials cannot arrive that way, because they are attached in `src/context.js` and a module never receives one, but caller-supplied text is caller-supplied text. A homoglyph defeats every escape. And a truncated value's fingerprint is collision resistance, not uniqueness, and never confidentiality.

**Binding.** `confirm: true` is accepted only for the stop it answers. Each stop records a pending approval, keyed by a sha256 of the canonical JSON of the call. For `execute` that is the action, the input (`undefined` read as `{}`), and the provider account id, or null on the first-party path, followed by the label when the call named one. For `disconnect` it is the service, the module, the stored account id, and the sorted list of `service/module` strings of every row bound to that account, a labelled row written `service/module@label`, the same rows `modules_ending` shows, followed by the label when the call named one. A call that names no label keys exactly as it did before labels existed. Canonical JSON sorts object keys and keeps array order, so two objects with the same members in a different key order are one input, and two lists in a different order are two. The approval is single use, it lasts fifteen minutes, and at most 256 are held. A confirm with no matching unexpired stop is answered with a fresh stop carrying `reason: unmatched_confirm`, and nothing reaches the module, the provider, or the catalog. A disconnect confirm whose bound set differs is that same fresh stop, carrying the current `modules_ending`, and nothing is revoked. The set is compared when the confirm arrives. A module hydrated onto the account while the revoke is in flight is bound to a credential that is ending, and its row is removed with the others; two gateway processes writing one store is the unlocked race `src/store.js` already records. A first stop carries no `reason` key. The confirmation key is computed only when a stop or a match is needed, and only after disclosure has withheld nothing, so every field in it is at most 32 levels deep. A `confirm: true` on a call that needs no approval runs and records nothing, because the same call without `confirm` runs too. `confirmation: once` still remembers the action after a matched confirm. The three entry paths, `confirmation: always`, `confirmation: once` on its first call, and a policy rule whose effect is `confirm`, are each bound. **`always` means always unless a standing approval covers the call**: a grant is the one way past a stop without `confirm: true`, and Standing approvals below says when one does.

The pending approvals live on the gateway instance as `pendingConfirmations`, in memory only. A restart between the stop and the confirm asks again. A host that builds one gateway per request hydrates and flushes `pendingConfirmations` the same way it does `confirmedOnce`.

**It lives in `src/disclosure.js`**, and the match lives in `src/gateway.js`. `execute` decides that a stop happens and on which of the three entry paths. It does not decide what a person is told. The stop in `execute` stays after `validateInput`, so the recorded key is a valid input, and it stays after the disclosure check above, so the key is not taken on a withheld value. In `disconnect`, a stored account id that contains a code point `src/disclosure.js` treats as unsafe is refused before any stop, `denied` with `reason: unsafe_account_id` and no `provider_account_id` field, and nothing is revoked. A safe id is still returned raw, because the caller echoes it back. A call with `confirm: true` checks `provider_account_id` first (missing is `invalid_arguments`, a changed binding is refused), and only then matches the pending approval, whose key names the modules as well as the account.

**None of it reaches the audit line.** `AUDIT_FIELDS` in `src/audit.js` is a closed set with no input field, and the pending key is not a member of it. The two version facts, `model` and `calibrated_model_version`, are members of that set, and a test asserts a rendered value does not appear in `audit.jsonl`.

## Standing approvals

A standing approval is a grant a person makes on purpose, after a warning, that lets calls inside its scope run without the stop above until it expires or is revoked. `skills/Standing Approval/` is how a session asks for one, uses one and ends one. The code is `src/standing-approvals.js` and `standingApprovalsTool` in `src/gateway.js`.

**Which actions can be granted.** Only an action whose manifest declares `standing_approval: { kind, summary }`, with an optional `caution`; without it, an action never can be, and `src/manifest.js` refuses the key on an action with no stop to remove. `kind` is `change`, `delete`, `send`, `pay`, `publish` or `grant_access`. The last five make a grant **heightened**: a stronger warning, and at most 7 days. Otherwise a grant lasts 90 days by default and at most 365. `summary` is the plain verb phrase the warning names the action by. `caution`, one or more sentences ending in a period, is what the person must know before granting that the action itself does not say, such as a workflow it can start; the warning carries each covered action's caution once, word for word.

**What a grant holds.** One `service.module`; its action ids, a module asked for whole expanded to its eligible actions when the grant is made, so a later release that marks another action never widens it; the summaries it was warned with; the connection's label, or null; the provider account id bound from that connection, so a reconnect to another account ends the match; the root; a Playbook or null; `where`, exact string values for top-level fields every covered action declares as a string, or null; its kinds; its dates; and `revoked_at`. A `where` value that looks like a credential is refused, so a grant holds no secret.

**How one is made.** `propose` checks the scope against the loaded manifests and the active connection, renders the warning, and records a pending approval keyed on the canonical scope in `pendingConfirmations`, the map a stop uses: single use, fifteen minutes, and hydrated and flushed by a host like any other. The key binds the warning's exact text as well as the scope, so a changed summary, caution or kind, or an end date that has moved past midnight, is a different proposal. `grant` with the identical scope and `confirmed: true` creates the grant only on that match, under an id derived from the proposal's key and its fixed expiry, and a store's `add` is idempotent per id, so a `grant` retried after a host failed to persist the consumed proposal finds the grant it already made and creates no second one; any other grant call is answered with a fresh proposal, marked `reason: unmatched_confirm` where `confirmed` was true. The warning is fixed text from `buildStandingApprovalWarning`, so every host shows the same words. `list` returns active grants with a plain summary each. `revoke` ends one at once and takes no stop, since it removes power. `readonly` may only list: `policy.default.json` denies it the op `standingApproval`.

**How a call matches.** In `execute`, after the disclosure check and before the confirmation key, a call that did not send `confirm: true` and declared a `root` is matched by `matchStandingApproval`. The oldest grant matches for which all of these hold: it is neither expired nor revoked; it names the action, and the action's manifest still declares `standing_approval`, with a kind the grant was made for, and with the summary, and any caution, the grant was warned with, so a connector release that rewords either ends the grant until the person grants again; where that kind is now heightened, the grant was made heightened and for at most 7 days; its label equals the call's; its provider account is the connection's; its root equals the call's `root`; where it names a Playbook, the call names that `playbook`; and every `where` field in the input is a string in its list. A grant covers the stop whatever raised it, the manifest's `always` or `once` or a policy rule's `confirm`, because the shipped default policy raises `confirm` for every destructive action. A policy `deny` returns before this point and is never covered. A match records no pending approval and leaves `confirmedOnce` unchanged. `disconnect`, `start_connect` and the first-party path never consult a grant.

**What a call under a grant leaves.** Its audit line carries `grant_id`, and every other line carries null. Its answer carries `standing_approval: { id, expires_at }`, a provider refusal included, and a non-object answer is wrapped as `{ result, standing_approval }`. Neither the warning nor a `where` value reaches the audit line.

**Where grants are kept.** On the local gateway, in `standing-approvals.jsonl`, append-only under its lock, apart from `connections.json`, whose whole-file rewrites would otherwise carry a stale copy of a grant back over its revoke; several local gateways on one machine share the file. A host passes `standingApprovals`, an object with `list`, `add` and `revoke`, and keeps them itself; the hosted service writes them only from this tool and its account page, never in the flush that rewrites a request's other state, so a revoke cannot be undone by a request that read the grant before it.

**What it does not do.** The root and the Playbook are the session's own declaration, and neither gateway verifies them; the skill is that check. A root or Playbook name follows `standards/conventions.md` Names, in ASCII letters. A call already past its read of the grants when a revoke lands can still run once under the grant it read. The person's yes reaches the gateway as `confirmed: true` from the session, the same trust the stop places in `confirm: true`; what keeps a grant to the scope the warning named is the binding to one identical, single-use proposal. A grant never removes a session's duties under the constitution's Irreversibles: before an update or a delete the session still reads the target and names what will be lost.

## Roles and policy

`--role` selects `runtime` or `readonly`; `policy.default.json` decides what each may do, and `~/.wiser/gateway/policy.json` replaces those rules if present. Any other value, including `setup`, is refused. The one row a multi-user deployment flips is `startConnect` for `runtime`: on a laptop the person talking is the person connecting, and the shipped default allows it.

## Proving a call live

Connectors load once, when the process starts. A long-running gateway serves connectors stale: check `describe_action` on that process, then prove live with a fresh `gateway/server.js` over stdio, newline-delimited JSON-RPC, `initialize`, then `tools/call` with `execute`, and exit the client after the reply. An edited connector or a new action is not visible on the process that loaded the old tree, and the new action answers `needs_connector` there.

Give that fresh gateway, and any instrument gateway, a distinct `--harness`, so the classifier presence file a session is using survives. That file is named for the `--harness` label, per Everything the gateway writes. A reused label replaces the file.

A fresh gateway home is not an empty account: the default key file's provider syncs live grants. Run an instrument gateway that allows `execute` with `--provider local-file` and `--secrets` set to an empty directory, prove that a connector `execute` answers `needs_connect` first, and stop on any connector `execute` that returns `ok`.

Read the gateway policy before a local live proof; where it routes a service to the hosted endpoint, prove through that endpoint after the approved deploy, and never around it with a scratch `--home`. The policy is the one Roles and policy names. A denial is the proof's result.

## What a host keeps

The endpoint delivers the person's saved preferences to Claude Code and Grok in its instructions at connect; to claude.ai and Cowork, which share one registered client, in the first Wiser tool answer after each opening request; and to ChatGPT and Codex in every Wiser tool answer, as measured on 2026-10-10 and 2026-10-14. Receiving the list is not applying it.

Measured on 2026-10-10, Claude Code cuts MCP server instructions at 4,096 characters and marks the cut `[truncated]`, Grok cuts them at about 2,000 characters and flattens them to one line, ChatGPT cuts them at 512 characters, and Codex, claude.ai and Cowork pass none to the model, while each host acts on whatever it does receive. A tool answer is not one channel: ChatGPT shows its model only `structuredContent` where an answer has one, and drops the text items beside it.

Before relying on server instructions or on a tool answer, ask that host's model to quote what it received, word for word, and score nothing until that quote is in hand; keep server instructions under the smallest host cap, and put tool-answer text where each host shows it.

Measured on 2026-10-10, ChatGPT reuses one MCP connection from its install across every new chat, so text sent only when a connection opens reaches it once, at install, and a settings change reaches it only after the app's Refresh tools is pressed or the server is added again; where a host reuses its connection, deliver per call. An app created on 2026-09-26 was still opening every reply with that day's test marker on 2026-10-10, until refreshed.

In a live test, refresh each app after a settings change, and confirm that refresh by a fresh opening request in the service's log.

Measured on 2026-10-23, a Claude Code session that connected to the Wiser endpoint before a release kept the definitions it had read for tools that already existed, while it took a tool the release added: after the standing approvals release two such sessions listed `standing_approvals` but an `execute` with no `root`, so no grant could match, and a reconnect from the app's MCP menu did not refresh it; a new session read `root` and `playbook` from the same endpoint. After a release that changes an existing tool's inputs, start a new session, and check that the tool lists the input before relying on it.
