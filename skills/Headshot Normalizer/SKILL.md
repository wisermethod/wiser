# Headshot Normalizer

One square PNG per photograph, background gone, the face measured and set to the same size and the same place in the frame as every other photograph put through the same standard. A photograph too short to fill the frame at that standard still gets the standard, and the transparent band left below the subject is delivered and reported with its height, never closed by enlarging the face past it.

## Context

Use it when portraits have to sit together and look like they were shot together: a team page, a speaker wall, a board of directors, a staff directory, a row of author cards. The photographs arrive framed however their owners framed them, a tight crop and a full-length shot in the same batch, and what makes the wall read as one wall is that every face ends up the same size in the same spot. A single portrait qualifies too, whenever it has to join a set that already exists.

Do not use it when the cutout is the deliverable. A photograph that only needs its background gone is `skills/Media Generator/`, which owns that request, chooses the model for it, and stops there; this skill takes the cutout as one stage of a frame it then measures and cuts. Do not use it for work a tool already owns: resizing, cropping, converting a format, and adjusting color are `tools/image-edit/`, laying one picture over another is `tools/image-overlay/`, and a portrait that does not exist yet is generated by `skills/Media Generator/`. Do not use it on a photograph whose subject is not the largest face in it, because the largest face is how the subject gets chosen and a group shot has no answer to that question; crop the subject out first.

Two properties bind every step below. Each photograph leaves this machine twice, once to a model host and once to a vision service, so a picture that must not be uploaded does not come here. And each photograph costs two billed calls, one generation run through `connectors/replicate/` and one annotation unit through `connectors/google-vision/`, spent whether or not the result is usable; a batch is that pair multiplied, and a re-run after a miss is another pair. Neither connector gates on spend, so the count is stated before the first call rather than confirmed.

Nothing here recognizes anyone. The vision call reports where a face is and never whose.

## Objective

One PNG per photograph at the destination the caller named: square at the frame's output size, transparent where the background was, carrying the subject's eyes the frame's stated distance apart, on the frame's eye line, centered horizontally between them. Verified by Success below, whose test is the product itself: two finished files from the same standard, laid one over the other, put their eyes in the same place.

## Inputs

Resolve each per the Credentials section of the connector that owns it, `connectors/replicate/` for the background removal and `connectors/google-vision/` for the face geometry, and pass the file each names to that connector's own commands as `--env <path>`. ## Identity

A retoucher preparing a wall, not a picture. A single portrait that looks good on its own and sits a few pixels off its neighbors has failed at the only thing this job is for, so the measurement is the work and the picture is the byproduct. Every number is read off the image rather than judged by eye.

## The Frame

Three parameters describe one frame. The defaults are one workable set and carry no authority beyond that; they are not a published standard and nothing here claims they are. A caller with their own standard states it in `<frame_standard>` and gets it.

| Parameter | Default | What it fixes |
|-----------|---------|---------------|
| Output size | 1000 | The side of the square, in pixels |
| Eye line | 392 | How far down the square the midpoint between the eyes sits |
| Eye span | 149 | The distance between the two eyes after scaling, in pixels |

The three are one composition rather than three settings, because each is a share of the square: at the defaults the eyes sit 39 percent down and 15 percent of the width apart. Raising the output size alone leaves the same face smaller in a bigger frame, so a caller who wants the same composition at another resolution scales all three by the same factor, and a caller who wants a different composition says which of the three is moving and why. State the frame back to the caller before the first billed call, because every photograph in a set has to run under the identical three numbers or the set does not match.

**This root ships tools and no connectors.** A `tools/` path this file names is present: `tools/AGENTS.md` indexes what ships, each tool installs what it needs on the first run that authorises it with `--install` (or `WISER_ALLOW_INSTALL=1` unattended) and reports what it would fetch and stops otherwise, so a tool that stops for consent is asking a question rather than failing; a tool that cannot run reports that itself rather than returning something wrong. **Wherever this file names a `connectors/` path, or a command that belongs to one, that capability is absent. Read the frontmatter as part of this rule, not beside it. Where the work in hand depends on something absent, or on a tool that stopped, say what cannot run and what it would have produced, name the gap it belongs to, and produce nothing in its place; where a mention only routes work away to it, that route is closed and nothing else stops. Do not approximate the missing output by hand, and do not carry a later step forward on a result the missing one never returned.

**And so is any value one of those absent sources would have stated**, a ceiling or a threshold included. A number that was going to come from something absent is absent too, and guessing it is the same defect as guessing the output: `tools/image-edit/` ships and will resize to whatever ceiling it is handed, so an invented one silently caps every frame below it.

1. **Settle the frame, the destination, and the count.** There is no default save location: ask for the directory, and for a name per photograph or the rule that derives one, since a set delivered under names nobody chose is a set nobody can wire into a page. Keep every intermediate file in a work directory per `standards/conventions.md`. Confirm the three frame parameters, then say what the batch will cost: two billed calls per photograph, named as a count before the first one. A set runs one photograph at a time through the steps below, under one frame; never change a parameter part way through a set.

2. **Take the background off.** Ask `connectors/replicate/` what it curates for background removal with `account.js defaults`, read that model's input schema with `models.js get`, and run it with `predictions.js run <model> --input <json> --output-dir <work directory> --env <path>`. The result is a PNG, because the transparency is the entire point of the step and a JPEG has no alpha channel to carry it. The model choice and its judgment belong to the connector's curated pin and to `skills/Media Generator/`; nothing about a model is decided or hardcoded here.

   The photograph has to reach the platform: inside the request, under the inline ceiling `connectors/replicate/` states, or at an address the platform can fetch. A larger local file with no address does not go as it is. Put the two ways forward to the user, a smaller rendition from `tools/image-edit/` or a reachable address, and say what the first one costs: the cutout can hold no more detail than what was sent, so a downscaled original caps the resolution of everything below.

3. **Find the eyes in the cutout.** One call, on the file from Step 2 rather than on the original:

   ```
   node scripts/faces.js detect <cutout path> --env <path>
   ```

   The cutout is what will be scaled and placed, so its pixel space is the one every coordinate below has to live in; measuring the original and applying the numbers to the cutout silently mixes two coordinate systems. If the cutout is past the size ceiling `connectors/google-vision/` states, detect on a smaller rendition from `tools/image-edit/` and multiply every coordinate that comes back by the cutout's width divided by the rendition's width before using it.

4. **Choose the face and measure it.** The connector returns a count and, per face, a detection confidence and the two eye positions, leaving every decision about them here. Discard any face missing either eye, since nothing below can be computed without both. Then:

   | What came back | What happens |
   |----------------|--------------|
   | No face, or none with both eyes | Step 7's unmeasured path. Nothing here is guessed |
   | One face | It is the subject |
   | Several | The subject is the one whose eyes are furthest apart, which is the nearest face and the one the photograph is of. Say how many were found and which was taken, because a second face is usually a bystander who is about to be cropped out |

   From the chosen face's two eye positions, compute the two numbers the frame is built from. The measured eye span is the straight-line distance between them, the square root of the squared difference in x plus the squared difference in y, which stays correct on a head that is tilted. The eye midpoint is their average in each axis. Report the chosen face's confidence with the result; a low one is a photograph worth looking at before it ships.

5. **Compute the frame.** All of this is arithmetic on numbers already in hand, and none of it costs anything.

   - **Scale.** The frame's eye span divided by the measured eye span. Above 1 the photograph is being enlarged, which the original's own resolution has to support.
   - **Scaled size.** The cutout's width and height, each multiplied by the scale and rounded to a whole pixel. The cutout's own dimensions arrive from `tools/image-edit/`, which reports the input's `sourceWidth` and `sourceHeight` on every run: a run carrying no operations is a plain conversion, so pointing one at the work directory reads the pair and costs a copy nobody has to keep.
   - **Offset.** Where the scaled picture's top left corner sits on the square. The scaled eye midpoint is Step 4's midpoint multiplied by the scale in each axis, so with the midpoint written mx and my: the offset's x is half the output size minus mx times the scale, and its y is the eye line minus my times the scale, each rounded to a whole pixel. Either number is signed, and a negative one is ordinary rather than an error: it means the scaled picture is wider or taller than the frame on that side and the frame keeps the part that falls inside it.
   - **The band below.** Add the scaled height to the offset's y. Short of the output size, the finished file will carry a transparent band under the subject, whose height is the output size minus that sum. Leave it and record its height for Step 8's report. Closing it would mean enlarging the picture, which multiplies the eye span by the same factor, or shifting it down, which takes the eyes off the eye line; either puts the file off the standard it was just normalized to. A band is visible and fixable with a taller original; an off-standard face is neither.

   Nothing closes a transparent margin on any side, so a photograph that does not cover the frame arrives with one. That is the frame reporting honestly that the original did not cover it; the fix is a larger original, never a stretch.

6. **Cut the frame.** One run of `tools/image-edit/`, which owns local pixel work, does the resize and the placement together:

   ```
   node scripts/edit.js edit --file <cutout path> --output <destination PNG> --resize <scaled width>x<scaled height> --canvas <output size>x<output size> --at <offset x>,<offset y>
   ```

   One run is enough because that tool applies its operations in a fixed order whatever order the flags are typed in, and the placement is last: the resize is third and the canvas ninth, so `--at` is measured against the picture the resize left rather than against the cutout on disk. At the defaults the canvas is `1000x1000`; a caller's own output size replaces both of its numbers, and the other two flags carry the numbers Step 5 computed for this photograph. Either number in `--at` may be negative, which is the ordinary case for a portrait scaled to put the eyes on the standard, and it is written with a comma because a position can be signed where a size cannot.

   The canvas is transparent, so the destination has to carry an alpha channel. Name a `.png`, which is this skill's product; a `.jpg` or `.jpeg` destination is refused by name rather than handing back a square whose transparency has been filled in.

   A run whose picture overruns the square names on stderr what it clipped, and still writes the file and exits 0 with its JSON on stdout. Two things stop it instead. A destination that already holds a file is refused rather than replaced, and that gate belongs to the tool, so ask before passing `--overwrite` rather than routing around it. And an offset that leaves no pixel of the picture on the canvas is refused with nothing written, which is the arithmetic rather than the frame: re-check the scale, the signs, and the scaled size against the cutout's real dimensions.

7. **When nothing could be measured.** A photograph whose face the vision call could not place still has a background-free cutout worth returning, and returning it is not the same as normalizing it. Fit the cutout inside the square with a ten pixel margin on its long edge, aspect ratio held, centered both ways. The fit scale is the output size less twenty, divided by the larger of the cutout's two dimensions; the fitted size is each of those dimensions times that scale, rounded; and each offset is half the output size less half the fitted size on that axis, rounded. Then the same run as Step 6, carrying those numbers instead:

   ```
   node scripts/edit.js edit --file <cutout path> --output <destination PNG> --resize <fitted width>x<fitted height> --canvas <output size>x<output size> --at <offset x>,<offset y>
   ```

   Both offsets are positive here and nothing reaches an edge, so a clip note on this path means a number is wrong. Deliver it saying in plain words that this file was not normalized and will not line up with the rest of the set. Then say why the detection missed, from what the photograph shows: a face turned too far, sunglasses, a hat brim, motion, a face too small in the frame. The way back is a different photograph, not a second run of this one, which would spend the same two calls to get the same answer.

8. **Deliver.** Open each finished file and check it: it exists where the caller said, it opens, and `tools/image-edit/` reports it square at the output size in PNG. **Transparency is not checked here**: no tool in this root reports whether a pixel is transparent, a PNG format field is not evidence that any is, and `standards` forbid judging it by eye. It is carried by the cutout and by the fit-and-center step rather than confirmed at delivery, and the transparent band this skill reports is computed from the measured frame rather than read off the image. Then report, per photograph, the path, the face count and the chosen face's confidence, the scale applied, the height of the band below whenever the placed picture did not reach the bottom of the square, and the two billed calls. For a set, report the same numbers as a list, because a scale far from its neighbors is the file worth looking at.

## Pitfalls

- **A centered substitute.** The product is that the eyes land on identical coordinates in every file. A centered crop, or a fit-and-center, looks finished and is normalized not at all, so it is never a stand-in for the computed offset when a run refuses or a number looks surprising. Step 7 is the one place centering is correct, and the file it produces ships labelled as unnormalized. Everywhere else the offset is the answer, and getting it wrong costs nothing to redo: the placement is free and the two billed calls that produced its numbers are already spent.
- **Reading the clip note as a failure.** The placement announces on stderr what it clipped and still writes the file and exits 0. On the main path that note is the normal case rather than a warning, because a picture scaled to put the eyes on the standard is usually larger than the square. Running the photograph again to make the note go away spends both billed calls for the identical answer.
- **Measuring the original.** Eye coordinates read from the photograph that went in do not describe the cutout that came back, and a model that trims or pads changes the pixel space silently. Every coordinate in Steps 4 to 6 comes from the file Step 2 produced, or from a rendition of it whose ratio has been multiplied back out.
- **Prose numbers over measured ones.** A frame standard someone remembers, a number in a brief, and the number a file actually carries are three different things. The frame is whatever `<frame_standard>` states or whatever the defaults are; nothing is inferred from a sample file by eye.
- **A batch under two standards.** Changing a parameter part way through a set produces files that each look correct and do not match, which is the one failure this skill exists to prevent and the hardest to see one file at a time. Closing a transparent band does the same thing without anyone changing a parameter: a photograph too short to fill the frame, enlarged or shifted down until it does, carries its eyes off the standard while looking finished alone. The band is never closed; Step 5 leaves it and Step 8 names its height.
- **The bystander.** The largest face wins, and in a photograph where the subject stands behind someone the largest face is the wrong person. Say how many faces were found; a count above one is the caller's cue to look before the file ships.
- **Rerunning a miss.** Both calls bill again and neither is random, so the same photograph returns the same failure at the same cost. Change the photograph.
- **An ambiguous request.** A request that does not say where the files go, which standard they follow, or which face is the subject gets a question before any billed call, never a default.
- **A connector this root does not carry.** Every `connectors/` path this file names, and every command that belongs to one, is capability this plugin does not ship; the `tools/` paths this file names do ship. Where a step depends on a connector, say which step cannot run and what it would have produced, then stop that step rather than approximating its output by hand. Whatever does not depend on it still runs, and where everything downstream does depend on it, the honest stop is the whole result. An improvised result is worse than a named gap, because nothing downstream can tell the two apart.
