# Before sending a build brief

Apply after Brief step 5 sets the output contract. A failed check is repaired before the brief goes.

- Does every rule hold on every live file it will meet? Yes: keep it. No: correct the boundary. Where two rules meet, state which wins; check ordering against where data becomes available, forbidden forms against real input, and write limits against every requested command, the suites' writes included.
- Does the brief fix manifest or tool text word for word? Yes: measure that exact text against the validator's bounds before sending it. No: no fixed-text measurement is needed.
- Will an executor compute a rule? Yes: sweep it by script over every small case before sending it; Verify step 1 checks the first real output. No: no sweep is needed.
- Does a fresh-context run rely on tool calls? Yes: show every call's exact argument shape as a literal example. No: no call example is needed.
- Does another session's checker pin a skill being changed? Yes: read it and carry its rules into the brief. No: add no checker rules.
- Will a skill chain run unattended? Yes: read every skill's steps and answer every question in advance, including any writing skill's frame, the reader's starting beliefs and the moment they meet the piece; an earlier run's silence waives nothing. No: no advance answer sheet is needed.
- Does the executor receive advance approval? Yes: name the request's files and every file the skill itself makes, by where it writes them. No: invent no approval.
- Will the builder write acceptance checks? Yes: derive expected counts from the file producing them, never literals from the builder's own run; do not freeze a source the plan permits changing. No: add no count rule.
- Will code compose member-facing words from parts? Yes: read the composed sentences in every state before handing over the parts. No: read the supplied copy as written.
