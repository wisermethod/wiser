# Brief contents

Apply while writing Brief step 4. Resolve an unanswered applicable question before sending the brief.

- Does the brief identify all work? Yes: name every file to read or change by absolute path, `<objective>`, `<targets>` and acceptance; copy the plan's permitted edits word for word. No: complete those fields.
- Is another session writing the checkout? Yes: cut a separate worktree in the plan's evidence directory from its recorded baseline commit; name its absolute path as the only writable plugin checkout in `<targets>`. Fetch `main`, diff it against that hash and read what landed since before building; a branch name never establishes the baseline. No recorded commit: settle it before building. No other writer: use the assigned checkout.
- Does the work produce evidence or records? Yes: name their destinations within `<targets>`; put proof logs and harnesses outside what ships, and regression tests in the shipped suites. No: add no evidence destination. In either case, the delegate leaves the plan to this session, which reads the evidence and updates it.
- Does a read bound exclude evidence the plan cites for a proved call? Yes: permit every cited file. No: keep the bound. Does it withhold a section? Yes: name the forbidden line range, never only the lines to read. No: add no range.
- Does the brief name a cited system's interface, fields, inputs or outputs? Yes: read and cite that system's own definition and the whole path producing those values, refusals included, never a definition line or a summary of names alone. No: go on. Does a repair touch a record's shape? Yes: check the brief against that shape's binding conditions before sending it. No: go on.
- Is evidence being handed to a reviewer? Yes: select it with the verifier's own selection code, never a packet-specific selection rule. No: add no packet selector.
- Will text ship? Yes: use neutral examples in the brief; before review, search the diff for the organisation names and evidence-file names the source records hold, bare filenames included, and remove those traces. No: no shipping-text sweep is needed.
- Is the brief ready to send? Yes: require reading relevant files first, running relevant checks, fixing what breaks, preserving folder layout, and never printing, copying or committing `.env` contents or anything under a root named memory; authorize no deploy, external message or write outside `<targets>`. If a script assembles it from a template, split on the marker's whole line, such as `\nTEMPLATE BEGINS\n`, never its bare string. No: finish it first.
