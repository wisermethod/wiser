# Tools

Deterministic operations that skills and experts call; `standards/primitives.md` owns the type's definition, invocation rules, and frontmatter. The directory is flat, and the index below is grouped by category.

## What a tool installs, and where

A tool ships its manifest and never its packages. Dependencies install on the machine that calls the tool, on the first run that authorises it with `--install`, into that tool's own directory: `node_modules/` for a Node tool, a virtual environment for a Python one. Installing the plugin installs none of it, and a tool nobody calls costs nothing.

Two consequences a caller should expect. The first use of a tool is slower than the rest, and a tool whose dependencies are large enough to need a system component, a browser build, an audio decoder, a speech model or Keynote, says so in its own `SETUP.md`. And a tool that needs something npm cannot install, an audio decoder or a browser build, names that dependency and the one command that proves it present, rather than carrying install steps that rot.

**This plugin's directory has to be writable.** A tool that carries dependencies installs them beside its own scripts, so a copy of this plugin installed where the user cannot write can answer `help` and nothing else. A tool that declares no dependency runs anywhere; each tool's own `package.json` or `requirements.txt` says which is which, and the index below names the tools rather than their dependencies. Installing through a plugin manager into the user's own space satisfies this, and a tool that cannot write says so in as many words rather than reporting a broken install.

**Dependencies are per copy, not per machine.** A tool installs into the copy of the plugin it was called from, so a second copy installs again, and a plugin manager that keeps each version in its own directory means an update starts from nothing. The cost is paid mostly in download time on the first use after an update, since the manager removes the version it replaced along with the packages inside it. It is not paid only in download time: npm's own cache and the browser build in the table below live outside any one copy, so they are not removed with it and they are not re-downloaded for the next one either.

## Everything a tool writes, and where

**This is the authoritative list, and no other file in this repository restates it.** The rule that makes that checkable: **a tool's own `TOOL.md` or `SETUP.md` that mentions an install, a cache, or any write other than the deliverable the caller named must point here for it rather than describe it.** The eighteen tools that install something all point here; the five that install nothing and write only what the caller named do not, and are right not to. A write inventory kept in two registers goes stale in one of them, and it has here: the version of this list that lived in each tool's own prose was wrong about npm's cache in six tools at once, and the version that lived in this file was wrong about the browser path in code for two commits after the prose was corrected.

The trial is the launch the tool is about to perform, headful or headless, because those run different artifacts. **What happens on a failure depends on WHERE IT HAPPENED, which is what the launch error can actually say.** The operating system refusing to EXECUTE the file names WHOSE fault it is, and the run reads that rather than the words. Bytes that are not a program (`ENOEXEC`) or a malformed image are the build's own problem and are installed. A binary present but not executable (`EACCES` with its own mode confirmed by `stat`) is intact, so nothing is replaced and the run prints the exact `chmod +x`. `spawn ... ENOENT` and Playwright's "executable doesn't exist" (read only when it is the whole first line of the error, never from inside another path) are trusted only when a `stat` of the path they name confirms the file is truly gone -- an unsearchable parent produces the same words over a complete browser. An absence the `stat` cannot confirm is the `'unknown'` outcome: it gets a plain install, which fetches only what is missing and replaces nothing, and never a forced replacement. Only a positively identified absent-or-broken artifact, after an install that had nothing to fetch, earns a forced replacement, **scoped to the artifact whose launch failed** -- `chromium-headless-shell` for a headless launch, `chromium --no-shell` for a headful one -- because a forced replacement of the whole set deletes every artifact before it refetches, and a repair of one has no business destroying a complete other. A host that cannot run the browser it already has -- a missing OS library, no compiler, an unwritable shim directory, a denied temporary directory -- is reported and nothing is installed, because replacing the build cannot fix the machine and a failed forced replacement deletes a working one. **AND A BROWSER THAT STARTS AND THEN STOPS IS NEITHER, SO NOTHING IS REPLACED.** A machine that kills Chromium -- no display for a headful launch, a security tool, an out-of-memory kill -- and a subtly damaged build produce the same sentence, and a gate round measured a forced repair on that signature deleting a complete, working browser out of the shared cache. The run says what is ambiguous and names the one scoped command, so a reader who has ruled the machine out replaces the build themselves. A tool must never destroy a working artifact on a guess; one typed command is the smaller cost. | wherever Playwright puts it, which this repository does not choose and does not second-guess: `PLAYWRIGHT_BROWSERS_PATH` if that is set to a path, `<tool>/node_modules/playwright-core/.local-browsers` if it is set to `0`, and otherwise the platform default under Playwright's own cache root, `~/Library/Caches/ms-playwright` on macOS, `$XDG_CACHE_HOME/ms-playwright` or `~/.cache/ms-playwright` on Linux, `%LOCALAPPDATA%\ms-playwright` on Windows | `Browser Control`, `deck-export`, `html-to-png`, `mermaid-to-png`, `svg-to-png`, `web-screenshot` |

**Three of those thirteen write to a path this plugin derives rather than one the caller typed**: `image-overlay` onto its own `--base`, `keynote-render`'s `zArchive/` beside the `--deck`, and `Content Harvester`'s bundle beside the request file. Each is refused, gated, or documented at its own tool; none is a surprise the caller cannot see coming, and all three are here because a derived path is exactly the kind a write inventory loses.

**Three of those thirteen are outside this plugin, and the rest are not.** They are npm's own cache, the session token, and, unless `PLAYWRIGHT_BROWSERS_PATH=0`, the browser build. The Linux shims used to be a third; they are now built inside the tool that needs them, which is why the row above names `node_modules/` rather than a cache path. **The three caller-named rows** -- the deliverable, the browser profile, and the trace archive -- are wherever the caller pointed them, which is outside this plugin in normal use but is the caller's choice rather than this plugin's. They are named here rather than described by position: this sentence used to say "the last three rows", and after four rows were added the last three had become the three DERIVED ones the paragraph above calls out, so a verifier reading it skipped exactly the writes a write inventory exists to surface. **The plugin directory still has to be writable**, because the node package, Python package and shim rows land inside it, so a tool that carries dependencies cannot work from a read-only install. A tool that declares no dependency runs anywhere.

**The per-platform browser path is Playwright's, not this repository's**, and no script here recomputes it. It is stated because an earlier revision of this file named the Linux path for every platform, which is wrong on the one platform `keynote-render` requires, and because the fix to that revision corrected this sentence and left the six copies of `scripts/lib/browser-runtime.js` hardcoding the Linux path in code for another two commits. Those copies no longer compute a cache path at all: each **walks up from its own file to the nearest `package.json`**, which is the tool's own manifest, and builds in the `node_modules/` beside it. It is worth saying what that replaced, because this paragraph described the replacement wrongly for three gate rounds: an earlier revision asked Node where `playwright` had resolved from, which is correct under `npm ci` and wrong under a store-linked layout, because `require.resolve` returns the realpath and the shims would land in a shared package store. Walking to the manifest asks no resolver and reads no environment variable, so it is right under every package manager.

**No install happens without someone authorising it.** A tool that has not been installed yet reports what it would fetch, from where, into which directory, and how large it is, and stops. `--install` on the same command authorises it and that run then finishes the work; `WISER_ALLOW_INSTALL=1` authorises it for an unattended run. A script cannot ask, because nothing here reads stdin and a run with nobody watching has to fail rather than wait, so the report is the question and whoever is driving the tool puts it to the person. **Three kinds of download are authorised by that one answer, and they are the whole of it**: a tool's own packages, the Chromium build a browser tool drives -- which `npm ci` does not fetch, because `playwright` carries no install script -- and the speech model weights, which `pip install` does not fetch either. Each is reported with its host and its size before it happens, and `--install` authorises whichever of them this run actually needs and then finishes the work. This is why nothing in the table below can arrive on a machine unannounced.

**The hosts an install reaches are named here for the same reason the paths are, and the list is per runtime rather than one line.** A Node tool contacts `registry.npmjs.org`. A browser tool also contacts `cdn.playwright.dev`, for the Chromium build, which `npm ci` does NOT fetch: `playwright` carries no install script, so the tool runs Playwright's own installer under the same authorisation, in the same run. `Transcribe Audio` runs Python and contacts `pypi.org` for the index and `files.pythonhosted.org` for the wheels themselves, and on first use of a given model it downloads weights from `openaipublic.azureedge.net`. No tool's own file may say it makes no network request without saying "after the first-run install", because the first run is exactly when it does. **An egress allowlist needs all six: `registry.npmjs.org`, `cdn.playwright.dev`, `playwright.download.prss.microsoft.com`, `pypi.org`, `files.pythonhosted.org` and `openaipublic.azureedge.net`.** The Microsoft host is Playwright's own fallback and the row above names it; an earlier revision of this sentence said five and left it out, which is the same defect one host smaller. An earlier revision of this paragraph named the first two and called them the whole of it, which left the Python tool failing three times in a row against an allowlist built from this file.

**One host is reached at RUN time rather than install time, and it belongs here for the same reason the install hosts do.** A deck is an HTML file the caller owns, and a deck may name any asset host it likes; the starter deck this repository ships in `skills/Create Presentation/starter-deck.html` names **`cdn.jsdelivr.net`**, which is where it loads reveal.js and its themes from. So `deck-export` and `html-to-png` rendering that deck reach `cdn.jsdelivr.net` on a run that installs nothing, and an egress allowlist built from the install list alone renders a blank deck rather than failing loudly. **There is a second, and it was found by round 9 in the paragraph that had just been written to name the first**: `skills/Visualizer/rendering.md` builds its diagrams from five libraries on **`cdnjs.cloudflare.com`** -- Cytoscape, Dagre, D3 and vis-timeline -- and `skills/Visualizer/SKILL.md` routes the result to `html-to-png`. Two run-time hosts, then: **`cdn.jsdelivr.net` and `cdnjs.cloudflare.com`**. Neither is an install host and neither is this plugin's choice; both are named once here because a register that names one of two is the failure this paragraph exists to prevent. It is not an install host, no script here fetches from it, and it is the deck's choice rather than this plugin's -- which is exactly why the register has to name it once instead of leaving it to be discovered.

**An install writes nothing this repository ships.** A Node tool installs with `npm ci`, which builds `node_modules/` from the lockfile exactly as recorded and never rewrites it; `npm install` does rewrite it, and every lockfile here is a file this repository ships, so a tool that installed with `npm install` would dirty a tracked file in your own clone merely by being called. Install every tool and `git status` stays clean. That is a guarantee rather than an observation, and `SETUP.md` names `npm ci` for the same reason wherever it gives the command by hand.

`system/templates/Script Contract.md` is the contract every one of these scripts follows, and it is the file to read before writing or changing one.
