# Connecting HeyGen

Connect Account owns the human grant in its own turn. The connector has six modules and thirteen actions: speech, voices, avatars, assets, videos and account.

## On HeyGen, first

1. Identify the API workspace holding the intended instant voices and existing avatars. **This key bills HeyGen's API wallet, separate from any HeyGen web subscription.** It uses your own workspace quota; Wiser supplies no credits, upgrades no plan and changes no top-up setting. Check commercial entitlement separately.
2. Create a restricted API key with exactly `voices:write`, `videos:write`, `assets:write`, `avatars:read` and `account:read`. Write includes resource reads. Exclude `avatars:write`, unrelated resources and `*:*`. All six bindings declare write because that is the shared key's intended privilege. Read action risk does not make its credential read-only.
3. During connect inspect `account.permissions`: custom mode and that exact scope set establish the intended restriction. Full, read-only, missing or broader grants require correction before relying on this description. Never paste a key into chat or a root file.
4. Before paid use establish this key's self-serve USD API-wallet billing basis and disclose the selected rate/estimate. Instant speech is bounded to 5,000 characters: at the rates read 2026-10-28, USD 0.075 for `heygen-voice-1`, USD 0.020 for paid Turbo, excluding taxes. Turbo Free's USD 0 offer ends 2026-11-30 and is not a permanent entitlement. Unknown, professional/minute or contract pricing is outside this route. A wallet read is advisory, not a reservation; concurrent use and delayed settlement can change it. An unchanged balance does not prove a free paid call. Check cloning capacity and current price before creating a resource; never delete an existing clone merely to fit a test.

**One blueprint per toolkit, not per module**, and for a toolkit the provider already ships there is nothing to prepare: the gateway creates the blueprint on the first connect that finds none. A second blueprint on one toolkit makes every module on that toolkit unconnectable until it is removed, with a `vendor_error` naming the toolkit and the count.

## Through the gateway

1. Say “Connect HeyGen” and name `speech`, `voices`, `avatars`, `assets`, `videos` or `account`, and a workspace label if appropriate. The member may be asked to connect.
2. The skill calls `start_connect`. Open its hosted link in your browser and enter your workspace API key only on that page. The gateway's provider holds it and injects `X-Api-Key`; the connector never receives it.
3. The skill calls `connect_status` and inspects the actual ACTIVE bindings, permissions and wallet. Each module has its own record. A labelled connect binds all six modules under that label to one credential. Revoking that credential ends its bindings together. An unlabelled module may require its own Connect Account turn; do not infer bindings from another process or a scratch store.
4. Use local stdio for speech output, clone uploads, narration asset uploads and MP4 downloads. Both output actions refuse without local output before provider access. A hosted service must withhold all four local actions, including `heygen.voices.add` and `heygen.assets.upload_audio`, before discovery/execution reaches filesystem or provider access. That separate service integration is not claimed by this connector. The nine other JSON actions, including both remote video-create alternatives, need no local file.

The gateway loads the connector on process start; use a fresh local gateway after installing it. `node gateway/server.js --check` from the plugin root checks loading without connecting. Attaching the local gateway is Set Up Connectors; it is not a vendor grant.

## The route this connector does not use

No OAuth, custom toolkit registration, credential unwrap, local vendor-key file, direct credentialed HTTP or catalog execution fallback is used. A key in conversation is never a route.

## Consent, limits and failures

The cloning workflow asks once for the person's voice-cloning consent and keeps its record; the connector adds no repeated ask or evidence upload. Creation and deletion need matched gateway confirmation every time. Creation acknowledges acceptance, not readiness; poll `voices.get` through PENDING to ACTIVE or FAILED. Before deletion read and identify the clone by id. A 2xx clone answer with a valid voice id acknowledges acceptance. Only `videos.create` supports a production-scoped pay standing approval; the paragraph below describes it.

One MP3/WAV upload is 1 to 3,000,000 bytes; every serialized proxy envelope is capped at 4,100,000 bytes; speech WAV output is capped at 67,108,864 bytes and MP4 download at 268,435,456 bytes. Narration uploads are one multipart file with fixed narration.mp3/narration.wav basename and matching MIME. Keep the returned asset id if video submission fails; assets are retained with no cleanup action. Large WAVs refuse; prepare and name a smaller complete MP3 explicitly, with no automatic transcode or chunking. `CONNECTOR.md` describes the physical-file, container and address restrictions. The vendor's larger limits cannot override these. Rate limits and concurrency depend on the workspace and free-model capacity; no fixed quota is promised. On 429 inspect quota and decide explicitly whether to retry. On 401/403 inspect key/workspace permissions; on 402 inspect the wallet; on 409 review the idempotency key/body; on 413/422 inspect size/requirements. No automatic retry after timeout, 5xx or ambiguous failure. `needs_provider_capability` means the provider lacks a required safe capability, not permission to switch auth routes. Never record a media address or raw failure.

## Avatar IV or Avatar V billing and one approval per production

Before video creation the caller chooses Avatar IV (`avatar_iv`) or Avatar V (`avatar_v`), never defaulted, and discloses the selected engine, look/type, rate and expected duration. Rates read 2026-10-29 at 720p/1080p: Avatar V custom video avatar (`digital_twin`) USD 0.12 a second; Avatar IV custom video avatar (`digital_twin`) or studio avatar (`studio_avatar`) USD 0.0805 a second, photo avatar (`photo_avatar`) USD 0.0385. No Avatar V rate is published for photo or studio avatars; for either, disclose USD 0.12 a second, the one Avatar V rate published, and state that the selected type's rate is unpublished. An asset id and script length do not cap billable duration; 30 minutes at the highest rate, USD 0.12 a second, is USD 216.00 for scale, not a spending guarantee. A separate script-voice debit is unmeasured. The implementation requires a positive self-serve USD API wallet; it cannot reserve balance or infer a whole render's cost from the published input. HeyGen enforces sufficiency, concurrent use and delayed settlement still apply. It never switches engines or retries a billed call automatically.

`videos.create` keeps confirmation always. To approve one production, ask Standing Approval for `heygen.videos.create`, the root and optionally the production's Playbook. The heightened pay warning lasts at most 7 days and needs your yes to that exact proposal. The summary is "create HeyGen avatar video charged to your HeyGen API wallet" and the caution is:

> Each covered call spends wallet dollars with no stop per call. Rates read 2026-10-29: Avatar V $0.12 a second; Avatar IV $0.0805 for a custom video or studio avatar, $0.0385 for a photo avatar. The wallet's balance is HeyGen's only ceiling.

Covered calls carry the root and any scoped Playbook. A call without root stops. You can revoke the grant at any time; its expiry/revocation ends coverage. No other HeyGen action declares one; speech has confirmation none and needs no grant. Asset upload still requires its own matched confirmation. Video polls/downloads reuse the accepted id; a failed download never rerenders. Clone id compatibility with script video was measured once on 2026-10-28, not promised for every voice. Expired-address renewal is unverified. Creating or training a person's avatar is excluded.

## Revoking

**Revoke through the gateway.** `disconnect`, with this service and any of its modules, revokes the credential at the provider and removes every local record of it.

- **It ends every module bound to that credential and not only the one you name.** It stops first and lists them in `modules_ending`. **That list is what you approve**: if anything else is bound to the credential before you answer, nothing is revoked and it stops again with the new list. The answer reports what was actually removed.
- **If someone wants one of those modules kept, their request cannot be met as asked, and saying so is the answer.** The credential is the unit; there is no way to end part of one. Two routes work. Either agree that both end, or first connect the module they want kept on a credential of its own, `start_connect` for that service and module and then `connect_status`, and only then run `disconnect`, **naming a module still on the old credential**, checking that `modules_ending` no longer lists the one you moved. **A labelled connection moves as one**: connecting again under a label moves every module of its toolkit under that label, so to keep one module out of a labelled connection, connect that module with no label first, then `disconnect` naming the label. **Do not approve the teardown hoping it spares one**, and do not take the vendor route instead, which is broader rather than narrower.
- **The vendor route below does not reach the same set, and may reach further.** `disconnect` acts on one provider account, and that account is what defines its scope; `modules_ending` reports the local bindings known to it when it asks. Rolling or deleting a credential at the vendor acts on everything that credential authorises, which can include modules bound to a different provider account, other machines, and other people. **`modules_ending` does not describe the vendor route**; before taking it, work out what else uses that credential.
- **It acts on one credential.** A service connected more than once needs one `disconnect` per credential. **`list_connections` shows what the gateway has recorded and nothing more**: it cannot establish that no credential for this service remains at the provider, because discovery lists only ACTIVE accounts, skips a toolkit holding more than one, and adds nothing when the provider cannot be read. To be sure a service is gone, check at the vendor. Do not read one teardown, or an empty listing, as removing a service entirely.
- **Revoking is not scoped to this workspace.** The credential lives at the provider, and the store is per person rather than per workspace, so ending it can end access from another machine or another workspace using the same grant. Settle that before approving.
- **It removes nothing locally unless the provider confirms the credential is gone**, so a grant that is merely suspended keeps its records.
- **A finished teardown says what it established, in `credential_revoked`.** `yes` means every step the provider reported succeeded. **`unknown` means the provider's record of the credential is gone and an earlier step failed**, so the credential may still work at the vendor even though nothing here points at it any more. Removing the local rows is right either way; **`unknown` is not a completed cutoff**, and the vendor route below is what finishes it.

**At the vendor instead**, if you would rather, or if `disconnect` answers `needs_provider_capability`, meaning this provider will not revoke this credential for you. Delete or rotate the workspace API key in HeyGen API settings, after checking everything else that uses it. Afterwards run `connect_status` for each module you revoked and read what it returns: it asks the provider and records the answer, so the row stops reading ACTIVE only once the provider agrees, and a provider error leaves it unchanged. A `how` field on the gateway's answer is the adapter's own words; where it names a route this guide does not list, the two disagree and that is worth reporting rather than following.
