# Script Contract

Fixed rules for every script a tool ships, in every runtime. Tools cite this file by the pointer at `system/templates/Script Contract.md`; none restate it. What a user meets when running a script is `tools/RUNNING.md`, which this file governs. Connector modules attach their clauses at the end of this file; they are not tools and they do not install.

## Rules for every script

**Self-contained.** Scripts import Node built-ins, their own directory's `node_modules/`, and files inside their own tool directory. The allowed imports outside a tool directory are `tools/lib/` and a shared runtime's packages in its person-scoped runtime directory (`tools/AGENTS.md`). Nothing else. No other import reaches outside the directory and no path into another root is hardcoded.

**Dependencies.** Before importing any package, the entry script checks for one named package's own `package.json` under `node_modules/`, never for the `node_modules/` directory itself, and a tool with more than one subcommand runs that check only for the subcommand that imports the package, so a subcommand that needs nothing never stops for an install another subcommand needs. A package a shared runtime supplies is checked in the active runtime: an existing copy-local install first, then the person-scoped runtime, each accepted only when Playwright's own package.json version equals the shipped lockfile's node_modules/playwright version. New shared browser packages install in `runtimes/browser-<key>/` under the platform user-config directory `gateway/SETUP.md` names, keyed by the first 16 hex characters of the shipped lockfile's SHA-256. Missing, the script **reports what an install would fetch and stops**; it does not install on its own account without the plugin's consent marker. Consent is `.wiser-consent` in the platform user-config directory: one JSON object with `scope: "person"`, the date and the tool that wrote it, mode 0600 in a directory created mode 0700 where absent. It covers every tool in every copy. On POSIX both the user-config directory and the marker must be owned by this user and not writable by group or others; the directory must be a real directory, never a symlink. Read the marker through a no-follow open, check the opened file's own fstat for a regular file and those ownership and mode rules, then read from that descriptor. Write a new temporary file inside the checked directory with exclusive create and no-follow (O_CREAT | O_EXCL | O_NOFOLLOW), mode 0600, then rename over the marker. On Windows, where the POSIX ownership and mode checks and the no-follow open do not apply, the marker is trusted by its location in the person's own profile, a link included. The copy marker at the plugin root remains valid when its recorded realpath matches this copy; a different realpath is ignored. **Consent is required and the script cannot ask for it**, because nothing here reads stdin and a run with nobody watching must fail rather than wait. So the report is the question: name the packages, the hosts they come from, the directory they land in, and the size where it is large enough to matter, then exit 1. Whoever is driving the script puts that to the person and re-runs with **`--install`**, which authorizes the install **and completes the run**, or sets **`WISER_ALLOW_INSTALL=1`** for an unattended one. Either answer attempts to write the person marker and the matching copy marker. If the person marker cannot be trusted or written, the authorised install says so on stderr in one line, with the reason: the copy marker then covers this copy alone where it could be written, and otherwise this run alone. Every install report and --install help states: Wiser asks once per person; a yes covers this install and later installs by any Wiser tool in any copy. `help` never reads the marker. A survey `check` without `--install` never writes it; a `check --install` that installs is an authorized install and writes it like any other. The marker is written at the moment an authorized install runs, after the command's flags have been read, so a refused command never writes it. A script must never demand a second run after an install it was authorized to make: the packages import dynamically, below the check, precisely so the authorized run can finish the work. `--install` is a bare flag every entry script that installs accepts and documents in its own help; a script that installs nothing refuses it by name like any other unknown flag. **`npm ci` and never `npm install`.** That install writes `node_modules/` inside the tool directory. Only a person-scoped browser install is built in a temporary sibling and renamed into its runtime directory when complete; an incomplete final directory is removed and publication retried once. Before installing, remove only this key's temporary siblings older than one hour. A tool-local npm ci writes directly into the tool's node_modules/, and npm also writes its own download cache and logs wherever npm is configured to keep them, which is outside the plugin. What it does not write is the lockfile: `npm ci` builds the tree from the lockfile exactly as recorded and never writes to it, while `npm install` may rewrite the lockfile, and a lockfile is a file this repository ships and tracks. `npm ci` also requires the lockfile to exist and to match the manifest, which is the right failure: a tool whose lockfile is missing or stale should stop rather than resolve something new. Never start a second command in the same tool while a first-run install is running.

**System dependencies.** A runtime a script needs beyond Node and npm (pandoc, ffmpeg, a Python interpreter, Keynote) is declared in the typed file's Dependencies section: the name, what needs it, and the one command that proves it is present. A script runs that check after help parsing and only on a command that needs the dependency; missing, it fails by naming the dependency and its check command, never with install steps. Install walkthroughs are never written into a primitive; they rot as platforms change. When a check fails, the agent reads the dependency's own current documentation when it is reachable, runs whatever install the host can run itself, machine-level changes only with the user's approval, and hands the user only the smallest step the host cannot; documentation unreachable, it stops and reports the dependency, the failed check, and that guidance could not be fetched, never inventing steps from memory. A primitive whose scripts need only Node and npm carries no Dependencies section.

**A version-matched artifact is not a system dependency, and the difference decides who installs it.** A system dependency is machine-level: one copy serves every plugin, its version is the machine's business, and a script that tried to install it would be changing the machine on the user's behalf. An artifact a pinned package resolves is the opposite: it belongs to that package's own version, the package's own installer puts it in the package's own place, and no other plugin is affected. Playwright's Chromium build is the second kind, since `playwright` carries no postinstall script and `npm ci` fetches no browser, and so are a Python package's model weights. The script installs those under the same `--install` consent as the packages and in the same run: name them in the consent report with their size and their hosts, ask the package's own installer for the filename rather than building that name here, and decide whether they are usable by using them, in the shape the tool is about to use them, because a headless launch and a headful one run different binaries. A Wiser default directory named in the constitution and in `tools/AGENTS.md` is the installer location when the caller omitted a path; an explicit absolute path still wins. Every artifact counts, because an interrupted download leaves a set that is incomplete rather than absent, and the installer's own criterion is the test, because a looser probe never asks for the repair and a stricter one asks for a repair the installer declines. A probe that inspects what is on disk is wrong one layer down; where the package decides by trying, the script decides by trying. A failure alone does not earn an install: the script reads where the launch failed before deciding a replacement is the repair, and it never destroys a working artifact reaching for one.

**Runtimes.** Node is the default runtime and the one the templates ship. A script may use another runtime when the typed file's Dependencies section declares that runtime's interpreter per System dependencies above. The interpreter is the one dependency a script cannot check from inside itself; the agent runs the declared presence check before the script's first invocation. Every other rule here binds unchanged in every runtime: help before configuration, `--env`, the output and error discipline, the write rules. Packages beyond the runtime's standard library install into a first-run cache inside the primitive's own directory (for Python, a virtual environment beside the scripts), by the same pattern as the `npm ci` above, consent included: check one named package's own marker inside the cache; missing, report what an install would fetch and exit 1; on `--install`, `WISER_ALLOW_INSTALL=1`, or a valid person marker or matching copy marker, create the cache, install, and finish the run. **The installer's own cache is part of what installs, and it is not inside that directory unless the script puts it there.** pip's default download cache is `~/Library/Caches/pip` or `~/.cache/pip`, it survives deleting the virtual environment, and on one tool here it reached several hundred megabytes; npm's is `~/.npm` and is disclosed in `tools/AGENTS.md` rather than suppressed, because `npm ci` has no equivalent of `--no-cache-dir` that is worth the re-download across eight tools. So a non-Node runtime's install either switches its cache off (`pip install --no-cache-dir --disable-pip-version-check`, with `PIP_NO_CACHE_DIR`, `PIP_CACHE_DIR` and `XDG_CACHE_HOME` set in the child's environment so a variable cannot reopen what a flag closed) or adds a row to that inventory. It never states that nothing installs outside the primitive's directory while leaving the installer's default cache in place. A runtime's standard library is preferred over a package that only saves typing.

**Help without configuration.** `help` and `--help` are parsed and answered before the dependency check, so usage is available on a copy that has never been installed or configured.

**Unknown flags.** An option a script does not name is refused by that name, before any work, any dependency install, and any network request. The refusal points at the script's own help.

A tool's option set is closed, and the command's own help declares it. Every flag the command accepts is listed, and anything else is refused.

The typed file lists them too. Where the typed file groups or summarises, it still names every flag.

**Configuration.** Every command needing configuration or credentials takes `--env [path]`, passed as an absolute path. The agent resolves it from the workspace's Provides binding (the constitution's Workspace Model, which also owns the unbound default). Scripts never search for a configuration file and never fall back to a default location. Parse the bound file directly: its values never enter the process environment, a log, or the output (the constitution's Irreversibles). When `--env` is absent or names a file that does not exist, the script says which and tells the agent to resolve the binding instead of guessing a path.

**Output and errors.** Work that succeeds prints one JSON object to stdout and exits 0. `help` and `--help` print usage text to stdout and exit 0. Failure prints to stderr only, leaves stdout empty, and exits 1. A failure message names the cause and the fix; when the cause came from an external service it names the status and the endpoint called, never the raw provider message, which can carry a credential. A successful object must not imply an input the process discarded: input dropped, first-wins among duplicates, or otherwise not applied is either refused before success or named in the object itself. A script calls its `main()` only when the file is run as the program, never at import, where an `exit()` would end a test that imports the file, green.

**Defaults an engine fills.** Where a script returns a figure that an engine it drives computes from facts about a case, such as a tax, a quote or a score, and that engine fills any fact it is not given with a default of its own, no such default reaches the figure. Every fact the script sends is required of the caller, a zero included, and an engine's report that it defaulted one of them is a refusal, not a success. Does the engine also compute a case from a fact the script does not collect? Yes: for each such case the script takes the caller's attestation, one boolean per case from a closed set its help names, `true` where the case applies and `false` where it does not, and refuses before the engine starts when one is missing, is not a boolean, or is `true`. No: the required facts are enough. Listing defaults beside the figure satisfies neither, because the figure was still computed on them.

**State.** A state probe tells complete from merely present: widen a boolean to a tri-state or richer result rather than AND it with another condition at the call sites. Does a boolean have to be combined with another condition at the call site to tell two states apart? Yes: it is under-answering, so widen it, such as absent, complete and incomplete, and test each arm with one fixture of its own. No: the boolean already separates the states, and the call site uses it alone.

**Unchanged.** A re-run that reports `unchanged` checks that what it vouches for is complete and usable, and refuses when that is in doubt. Does this run report `unchanged`? Yes: make that check, and refuse rather than report success over a missing or unusable part. It reports a change, or it is not a re-run: this check does not apply.

**Matching a result.** Does an exit code or a structured field carry the fact? Yes: match that, and do not match the prose. No: the text has to be matched, so anchor on the token and ignore case.

**Where files are written.** Beyond the dependency install above, a script never writes inside its own directory. A script accepting an output path refuses one that resolves inside that directory; the agent passes a work directory in the owning root, per `standards/conventions.md`.

**Caller-named paths.** Every path a command accepts as a source or a destination is screened before anything opens it; the `--env` path itself is configuration, governed above, not a source. The screen canonicalizes the path against the filesystem, walking up to the deepest ancestor that exists, resolving it, and rejoining the components below, so a symbolic link anywhere in the spelling, including one standing in for a parent of a file that does not exist yet, collapses onto the real path it names; a path that cannot be canonicalized has not been cleared and is refused, never compared as the text it was spelled with. The canonical path is then compared by device and inode, the identity a hard link keeps and no spelling reaches, against the refused set: the file `--env` names; every file resolving inside the directory that holds it, which holds credentials and nothing else; and, for a destination, the primitive's own directory (Where files are written, above). The screen returns the resolved path, and the call site uses that value for every open, read, write, and transmit; a test against a filename runs on the resolved basename, never the caller's spelling. One decoupling: a filename a command transmits, an upload's display name or an attachment's name in a body, may keep the caller's spelling; the bytes always come from the resolved path. The screen answers for the moment it is called, so a file swapped between the check and the open is not caught. Accepted: the vectors this clause closes need only a link planted in advance, while the swap also requires a concurrent process writing in the work directory as the same user, who can already read that user's own credential file, so the race grants essentially no capability not already held; the fix, opening once and reading through the descriptor, would restructure every screen's read path and is not taken.

## Connector modules

A connector module is not a tool. It has no `--install`, no `node_modules/`, and no consent marker. The gateway that loads it has no dependencies. These clauses bind the module and the gateway's flags; they do not relax the rules above for tools.

**Imports.** A module imports Node built-ins and files inside its own connector directory. It does not import `tools/lib/` or anything else outside that directory. It never imports a provider adapter.

**Credentials.** A module never reads a credential file, never receives a token on `ctx`, and never writes one. `ctx.http` exists only when the manifest says `unwrap_token: true` and the provider can unwrap; the gateway attaches the value and the module never sees it. Vendor grants are the provider's. A local-file key is `--secret` or a Provides path, never a default directory in a root.

**Gateway flags.** `help` and `--help` print usage and exit 0 with nothing configured. `--check` validates manifests and policy, prints one JSON object, and exits 0; it does not create the project-key file. An unknown flag is refused by name. `--role` is `runtime` or `readonly`; any other value, including `setup`, is refused. `--home` is an absolute path, canonicalised, and refused inside the plugin, beside a credential file, or on a symbolic link. `--env` is optional when the platform user-config file exists. `--connectors` names extra connector directories. `--secret <service>=<abs file>` binds a local-file credential; `--secrets` names a directory of them. `--harness` is an audit label.

**Published input schema.** An action's `input` is the contract, not a description of one. The gateway applies it before the module runs, in `gateway/src/input-schema.js`, reading `required`, `type`, `enum`, `pattern`, `minLength` and `items`; `gateway/test/agreement.test.js` fails when a module enforces a rule its schema does not publish, and when a schema publishes a rule nothing applies. Four consequences bind a connector author:

- **Declare `additionalProperties: false` on every action.** The gateway refuses a key `properties` does not declare whatever the schema says, so a schema that leaves it open publishes a permission the system does not grant. A payload whose keys the vendor decides is one declared property of type `object`, not an open action; the gateway does not look inside it and the module judges what it holds.
- **A conditional requirement is published with `oneOf` or `anyOf`, and the module enforces it.** The gateway does not read composition, deliberately, because a module's own refusal names the field and the alternative in terms its caller understands. Publishing the choice is what makes it readable; the agreement gate is what proves the module applies it.
- **`maxLength` and `minLength` count code points, not UTF-16 code units.** A string of 351 emoji is 351 characters and 702 units, and a module counting `value.length` refuses a value its own declaration admits. `gateway/src/disclosure.js` and `connectors/google-cloud/index.js` already count this way; the rule lives here so a connector author reads it before writing the third.
- **A rule a schema cannot express is written down, not dropped.** Filesystem state, a value the module parses rather than matches, and anything the vendor decides belong in the action's `description` and in `CONNECTOR.md`. An unwritten rule is the one a caller meets as a refusal it cannot predict.

**Output.** `help` is usage text. `--check` and every tool result the gateway serves is one JSON object. A status object (`needs_connect`, `needs_provider`, `needs_confirmation`, `denied`, `needs_connector`, `needs_provider_capability`, `vendor_error`, `invalid_arguments`) is a stop, not a retry. `vendor_error` names the status and the endpoint, never the raw body. A module follows State, Unchanged, and Matching a result, under Rules for every script.
